2️⃣ How It's Stored (Workflow Definition in PostgreSQL)

When user saves the workflow, Angular sends this JSON to the Workflow Service:

{ "workflowId": "workflow-123", "name": "Daily Email Summary", "userId": "user-456", "nodes": [ { "id": "node-1", "type": "trigger", "position": { "x": 100, "y": 200 }, "config": { "triggerType": "cron", "cronExpression": "0 8 * * *" } }, { "id": "node-2", "type": "gmail", "position": { "x": 300, "y": 200 }, "config": { "action": "read", "filters": { "from": "client@example.com", "isUnread": true } } }, { "id": "node-3", "type": "gemini", "position": { "x": 500, "y": 200 }, "config": { "prompt": "Summarize this email: {{node-2.output.body}}", // 👆 References previous node's output! "model": "gemini-pro" } }, { "id": "node-4", "type": "http", "position": { "x": 700, "y": 200 }, "config": { "method": "POST", "url": "https://webhook.site/xyz", "body": { "summary": "{{node-3.output.text}}", // 👆 References Gemini's output! "originalEmail": "{{node-2.output.subject}}" } } } ], "edges": [ { "from": "node-1", "to": "node-2" }, { "from": "node-2", "to": "node-3" }, { "from": "node-3", "to": "node-4" } ] }
🔑 Key Points:
  • Nodes: Each service is a node with unique ID, type, and configuration
  • Edges: Define execution order (from → to)
  • Variable References: Use {{node-X.output.field}} to pass data between nodes
  • Stored in PostgreSQL: Workflow Service stores this in workflows table as JSONB

3️⃣ How Execution Works Step-by-Step

1
⏰ Trigger Service Fires

When: At 8:00 AM (cron job detected by Quartz Scheduler)

Action:

  • Trigger Service reads the workflow from PostgreSQL
  • Creates an execution event
  • Publishes to Kafka: Topic workflow-trigger
{ "workflowId": "workflow-123", "executionId": "exec-789", "userId": "user-456", "triggeredBy": "cron", "timestamp": "2024-02-26T08:00:00Z" }
2
⚙️ Execution Service Receives Event

Execution Service (Kafka Consumer) listens to workflow-trigger topic

When message arrives:

  • Fetches workflow definition from PostgreSQL using workflowId
  • Builds execution graph (DAG - Directed Acyclic Graph) from nodes and edges
  • Determines execution order using topological sort
  • Creates execution context to store intermediate results
// Java Pseudo-code in Execution Service WorkflowDefinition workflow = workflowRepository.findById(workflowId); ExecutionContext context = new ExecutionContext(executionId); // Build execution order: [node-1, node-2, node-3, node-4] List<String> executionOrder = buildExecutionOrder(workflow.getNodes(), workflow.getEdges());
3
📧 Execute Node 2 - Gmail Service

Execution Service calls Gmail Service via REST API

// Execution Service makes HTTP call POST http://gmail-service:8091/execute { "nodeId": "node-2", "config": { "action": "read", "filters": { "from": "client@example.com" } }, "credentials": { /* OAuth token from Credentials Service */ } }

Gmail Service Response:

{ "success": true, "output": { "emailId": "email-abc123", "subject": "Project Update from Client", "body": "Hi, here's the latest update on the project...", "from": "client@example.com", "timestamp": "2024-02-26T07:45:00Z" } }

Execution Service stores this in context:

context.setNodeOutput("node-2", gmailResponse.getOutput());
4
🤖 Execute Node 3 - Gemini Service

Execution Service resolves variable references and calls Gemini Service

// 1. Resolve template variables from context String prompt = resolveTemplate( "Summarize this email: {{node-2.output.body}}", context ); // Result: "Summarize this email: Hi, here's the latest update..." // 2. Call Gemini Service POST http://gemini-service:8092/execute { "nodeId": "node-3", "config": { "prompt": "Summarize this email: Hi, here's the latest...", "model": "gemini-pro" } }

Gemini Service Response:

{ "success": true, "output": { "text": "The client provided a project update discussing timeline changes and resource allocation for Q2.", "tokensUsed": 150 } }

Store in context:

context.setNodeOutput("node-3", geminiResponse.getOutput());
5
🌐 Execute Node 4 - HTTP Service

Execution Service resolves variables and calls HTTP Service

// Resolve all template variables POST http://http-service:8093/execute { "nodeId": "node-4", "config": { "method": "POST", "url": "https://webhook.site/xyz", "body": { "summary": "The client provided a project update...", "originalEmail": "Project Update from Client" } } }

HTTP Service makes external request and responds:

{ "success": true, "output": { "statusCode": 200, "responseBody": "Webhook received successfully" } }
6
✅ Complete Workflow Execution

Execution Service finalizes the workflow

  • Marks execution as SUCCESS
  • Stores execution history in PostgreSQL
  • Sends logs to Logging Service
  • Publishes completion event to Kafka (optional for notifications)
// Store in execution_history table { "executionId": "exec-789", "workflowId": "workflow-123", "status": "SUCCESS", "startTime": "2024-02-26T08:00:01Z", "endTime": "2024-02-26T08:00:15Z", "nodeResults": { "node-2": { "status": "SUCCESS", "duration": "2s" }, "node-3": { "status": "SUCCESS", "duration": "5s" }, "node-4": { "status": "SUCCESS", "duration": "1s" } } }

5️⃣ Key Takeaways

✅ Execution Order is Guaranteed

  • Edges define order: The edges array creates a dependency graph
  • Topological sort: Execution Service uses graph algorithm to determine sequence
  • Sequential execution: Node N+1 only starts after Node N completes successfully

✅ Data Flows Through Execution Context

  • Execution Context: In-memory object that stores all node outputs
  • Variable Resolution: Template engine replaces {{node-X.output.field}} with actual values
  • Available downstream: Any node can reference outputs from previous nodes

✅ Services Are Loosely Coupled

  • Integration services don't know about each other
  • They only implement NodeExecutor interface
  • Execution Service orchestrates everything
  • Easy to add new services without modifying existing ones

⚠️ Error Handling

  • Node failure: If Gmail Service fails, execution stops
  • Retry logic: Execution Service can retry failed nodes (configurable)
  • Error propagation: User sees which node failed in Angular UI
  • Partial execution: All successful node outputs are saved

6️⃣ The NodeExecutor Interface (Contract for All Services)

Every integration service implements this interface:

// NodeExecutor.java (Common Interface) public interface NodeExecutor { // Main execution method - called by Execution Service ExecutionResult execute(NodeConfig config, Map<String, Object> inputs); // Returns metadata about this node (for Angular UI) NodeSchema getSchema(); // Unique identifier: "gmail", "gemini", "http", etc. String getNodeType(); } // Example: GmailServiceImpl.java @Service public class GmailServiceImpl implements NodeExecutor { @Override public ExecutionResult execute(NodeConfig config, Map<String, Object> inputs) { // 1. Parse config String action = config.get("action"); // 2. Get credentials String oauthToken = credentialsService.getToken(config.getUserId(), "gmail"); // 3. Execute action if (action.equals("read")) { List<Email> emails = gmailApi.readEmails(config.getFilters(), oauthToken); return ExecutionResult.success(Map.of("emails", emails)); } } @Override public String getNodeType() { return "gmail"; } }

🎯 Summary

  1. User creates workflow visually in Angular (drag & drop nodes, connect them)
  2. Saved as JSON graph in PostgreSQL (nodes + edges)
  3. Trigger fires → Publishes event to Kafka
  4. Execution Service consumes event → Builds execution order from edges
  5. Calls each node service sequentially via REST API
  6. Passes data between nodes using Execution Context and variable templates
  7. Stores results in PostgreSQL for history
