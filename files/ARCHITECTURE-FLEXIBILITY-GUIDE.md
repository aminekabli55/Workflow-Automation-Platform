## 🧩 The Flexibility Model

### **Key Principle: "Standardized Interface, Flexible Data"**

Every integration service follows the same pattern:

```
┌─────────────────────────────────────────────────┐
│         STANDARD INTERFACE (Same for All)       │
├─────────────────────────────────────────────────┤
│  POST /api/{service}/execute                    │
│                                                 │
│  Input:  NodeExecutionRequest                  │
│  Output: ExecutionResult                       │
└─────────────────────────────────────────────────┘
         ↓                           ↓
┌──────────────────┐      ┌──────────────────┐
│  FLEXIBLE CONFIG │      │ FLEXIBLE OUTPUT  │
│  (What user sets)│      │ (What service    │
│                  │      │  returns)        │
└──────────────────┘      └──────────────────┘
```

---

## 📋 Standard Request/Response Structure

### **Input: NodeExecutionRequest (Standardized)**

```json
{
  "nodeId": "node-2",           // ← Standard (generated by UI)
  "nodeType": "gmail",          // ← Standard (service type)
  "userId": "user-123",         // ← Standard (who triggered it)
  "inputs": {                   // ← Standard (outputs from previous nodes)
    "node-1": {
      "trigger": "manual",
      "timestamp": "2024-03-02T10:00:00Z"
    }
  },
  "config": {                   // ← FLEXIBLE (user-defined per service!)
    // This is where flexibility comes in!
    // Different for each service type
  }
}
```

### **Output: ExecutionResult (Standardized)**

```json
{
  "success": true,              // ← Standard
  "error": null,                // ← Standard
  "output": {                   // ← FLEXIBLE (service-specific data)
    // This is where service returns its data
    // Different for each service type
  }
}
```

## 🎨 Flexibility in Action

### **Example 1: Gmail Service**

**What User Configures (config):**
```json
{
  "config": {
    "action": "read",           // User chooses: read, send, search
    "filters": {
      "from": "boss@company.com",
      "isUnread": true
    },
    "maxResults": 10
  }
}
```

**What Service Returns (output):**
```json
{
  "output": {
    "emails": [...],
    "count": 5,
    "subject": "First email subject",
    "body": "First email body",
    "from": "boss@company.com",
    "emailId": "abc123"
  }
}
```

**Flexibility:**
- User can configure: action, filters, max results
- Service returns: emails array + convenient first email fields
- Next node can use: `{{node-2.output.subject}}` or `{{node-2.output.emails[0].body}}`

**Flexibility:**
- User can call ANY API
- User can configure: method, URL, headers, body, auth
- Service returns: status code, response body
- Next node can use: `{{node-3.output.statusCode}}`

## 🔄 Template Variable System

### **How Nodes Reference Each Other:**

```json
// Node 2 (Gmail) runs first, outputs:
{
  "emails": [...],
  "subject": "Meeting Tomorrow",
  "body": "The meeting is at 3 PM"
}

// Node 3 (Gemini) can reference it:
{
  "config": {
    "text": "{{node-2.output.body}}"  // ← Template variable
  }
}

// After template resolution:
{
  "config": {
    "text": "The meeting is at 3 PM"  // ← Actual value
  }
}
```

**Execution Service resolves these automatically!**

## 📐 Design Pattern: Service Schema

### **Each Service Exposes Its Configuration Schema:**

```bash
GET /api/gmail/schema
```

**Returns:**
```json
{
  "nodeType": "gmail",
  "displayName": "Gmail",
  "description": "Read and send emails via Gmail",
  "category": "communication",
  "icon": "📧",
  "configSchema": {
    "action": {
      "type": "select",
      "options": ["read", "send", "search", "markAsRead", "addLabel"],
      "required": true,
      "default": "read"
    },
    "filters": {
      "type": "object",
      "properties": {
        "from": {"type": "string"},
        "isUnread": {"type": "boolean"}
      }
    },
    "maxResults": {
      "type": "number",
      "default": 10,
      "min": 1,
      "max": 100
    }
  },
  "outputSchema": {
    "emails": {"type": "array"},
    "count": {"type": "number"},
    "subject": {"type": "string"},
    "body": {"type": "string"},
    "from": {"type": "string"}
  }
}
```

**Frontend uses this to build the UI dynamically!**

## 🎯 User Journey: Building a Workflow

### **Step 1: User Drags Gmail Node**

Frontend calls:
```bash
GET /api/gmail/schema
```

Shows configuration form:
- Action dropdown: [read, send, search]
- Filters: from (text), isUnread (checkbox)
- Max results: (number input)

### **Step 2: User Fills Configuration**

User enters:
- Action: "read"
- From: "boss@company.com"
- Is Unread: true
- Max Results: 5

### **Step 3: User Drags HTTP Node**

Frontend calls:
```bash
GET /api/http/schema
```

Shows:
- Method: [GET, POST, PUT, DELETE]
- URL: (text input)
- Body: (JSON editor)
- Template variables available: `{{node-2.output.subject}}`

### **Step 4: User Configures HTTP Node**

User enters:
- Method: "POST"
- URL: "https://webhook.site/abc123"
- Body: `{"subject": "{{node-2.output.subject}}"}`

### **Step 5: Save Workflow**

Frontend sends to Workflow Service:
```json
{
  "workflowId": "workflow-123",
  "name": "Email to Webhook",
  "nodes": [
    {
      "id": "node-1",
      "type": "trigger",
      "config": {"triggerType": "manual"}
    },
    {
      "id": "node-2",
      "type": "gmail",
      "config": {
        "action": "read",
        "filters": {"from": "boss@company.com", "isUnread": true},
        "maxResults": 5
      }
    },
    {
      "id": "node-3",
      "type": "http",
      "config": {
        "method": "POST",
        "url": "https://webhook.site/abc123",
        "body": {"subject": "{{node-2.output.subject}}"}
      }
    }
  ],
  "edges": [
    {"from": "node-1", "to": "node-2"},
    {"from": "node-2", "to": "node-3"}
  ]
}
```

```typescript
// Generates form automatically
schema.configSchema.forEach(field => {
  if (field.type === 'select') {
    renderDropdown(field.options);
  } else if (field.type === 'string') {
    renderTextInput(field);
  }
  // ... etc
});
```

**No hardcoding!** Add new service = UI updates automatically!

## 🔧 Adding New Actions to Existing Services

### **Example: Add "Archive" action to Gmail**

**In GmailExecutorService.java:**
```java
return switch (action) {
    case "read" -> readEmails(request);
    case "send" -> sendEmail(request);
    case "archive" -> archiveEmail(request);  // ← New action
    default -> ExecutionResult.failure("Unknown action");
};
```

**Update schema:**
```json
{
  "action": {
    "options": ["read", "send", "search", "archive"]  // ← Add here
  }
}
```

**That's it!** Frontend picks it up automatically!

## 🎯 Summary: Flexibility Model

### **Standardized:**
✅ Request/Response structure (`NodeExecutionRequest`, `ExecutionResult`)
✅ API endpoints (`POST /execute`, `GET /schema`)
✅ Service registration (Eureka)
✅ Template variable syntax (`{{node-X.output.field}}`)

### **Flexible:**
🎨 Service-specific `config` (each service defines its own)
🎨 Service-specific `output` (each service returns what makes sense)
🎨 Actions per service (read/send/search for Gmail, etc.)
🎨 Authentication per service (OAuth for Gmail, API key for others)
🎨 UI generation (based on schema)

### **Result:**
🚀 **Add new service** = No changes to Execution Service or Frontend core
🚀 **Add new action** = Just update service + schema
🚀 **Users configure visually** = Frontend builds forms from schema
🚀 **Template variables** = Nodes reference each other naturally
